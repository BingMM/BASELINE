## 2026-04-22 Paper Re-read - Weighted Fit Uses More Than Fitted Sigma

The article wording supports the user's recollection that the weighted fit uses more than just the derived Gaussian `sigma`.

Relevant passages:

- Section 5.1.3, paragraph `[37]`, says the Step 1d weighted fit uses "knowledge of each semi-hourly fit" and that each semi-hourly value provides knowledge of both "the spread in the data" and "the width of the window used." This is broader than a single fitted `sigma`.
- Section 5.2.2, paragraph `[41]`, says the weighted smoothing uses a "non-trivial weighting" discussed in section 7.1 and that the uncertainty has two parts: instantaneous variance and a scaled variance from the history of the data.
- Section 7.1, paragraphs `[70]-[72]`, defines `v`, `d`, and `U = v + d`, where `v` is the instantaneous variance and `d` is a time-delayed or memory term. The author says `sqrt(U)` can be interpreted as a modified standard deviation.

Interpretation:

- For the yearly trend, the paper is explicit that the weighting is not a plain Gaussian-fit `sigma`; it is a variance-like uncertainty with memory.
- For the daily QD Step 1d fit, the paper does not give an explicit formula, but the wording strongly suggests that both the spread of the semi-hourly distribution and the window width should influence the weight.
- Therefore the current implementation should be treated as an approximation here, not a faithful reconstruction.

## 2026-04-22 Hypothesis - Step 1c May Need Center-Day Weighting

The user raised a physically motivated concern about Step 1c: the algorithm combines samples from multiple days to estimate the daily variation for one specific day and local-time bin. In the problematic N-component interval, the histograms often show two clear populations of opposite sign rather than one mode plus outliers.

Interpretation:

- if the sign of the daily variation can legitimately differ from day to day, then equal weighting of all days inside the Step 1c window may be causing modal-bin hopping between day-specific populations;
- in that case, giving higher weight to the day in question could stabilize the estimate for the target day without changing Step 1d.

Important caveat:

- the paper does not describe any center-day weighting inside the Step 1c histogram; the current reading is that all samples in the accepted window contribute equally.
- therefore this should be treated as a potential extension or fallback experiment, not part of the baseline paper-faithful reconstruction.

If tested later, the cleanest implementation would be to build a weighted histogram for Step 1c where each sample contributes a day-distance weight rather than a unit count.

## 2026-04-23 Step 2a / 2b Gap-Day Bug Fixed

Inspection of `figures/SM_step_2b.png` showed that daily Step 2a values were being generated inside calendar intervals with no actual data, and those gap-day values were then influencing the Step 2b weighted smoothing.

Cause:

- `step_2a()` iterated over every calendar day present in the time grid;
- it estimated a daily value from neighboring data even when the target day itself had zero finite `x_QD` samples;
- those synthetic gap-day nodes received nonzero weights and affected the Step 2b fit.

Fix:

- `step_2a()` now checks the target day before attempting the expanding-window estimate;
- if the target day has zero finite `x_QD` samples, it emits `NaN` with weight `0.0` and skips estimation for that day.

This is a real bug fix, not an algorithmic interpretation change.

- there is no extra time shift, timezone conversion, or alternate time base in the plotting code;
- therefore the bad timing in the figure reflects the estimator output itself, not a display bug.

Current interpretation:

- the fit is genuinely off in that chunk;
- the likely source is upstream in Step 1c node timing/bias or Step 1d smoothing/interpolation, not the plotting function.

## 2026-04-25 Root Cause - Post-Gap QD Distortion Was An Interpolation Bug

After a clean run, the user observed that the local QD looked fine until the first long missing interval around `2024-01-22 06:00` to `2024-01-28 12:00`, after which the fit became obviously wrong.

Cause found in the code:

- `cubic_convolution_interpolate()` was dropping NaN-valued nodes and then treating the remaining nodes as if they were still uniformly spaced;
- after the first long gap, that breaks the relationship between node index and actual time, so the interpolation basis is wrong for everything after the gap;
- separately, `weighted_gaussian_smooth()` was still producing smoothed values at missing target nodes, creating support points inside gaps.

Fix applied:

- `cubic_convolution_interpolate()` now preserves NaN-valued nodes in the regular node grid and only ignores them locally when forming the interpolation stencil;
- `weighted_gaussian_smooth()` now leaves missing/zero-weight target nodes as NaN instead of synthesizing smoothed values there.

Interpretation:

- this was a real post-gap interpolation bug in Step 1b / Step 1d style resampling, not a plotting issue and not a Step 1c cache issue.
- Because the expensive Step 1c results are unchanged, this should be fixable with a fast rerun that reuses the Step 1c checkpoint and recomputes Step 1d onward.

## 2026-04-25 New Side Effect - Rejected Step 1c Nodes Now Create QD Discontinuities

After the interpolation/gap fix, a new artifact showed up in `SM_QD_comp_20240218_20240219.png`, specifically `Bu` just after `2024-02-19 12:00`.

What is happening:

- raw `Bu` data are present throughout the inspected interval;
- the Step 1c series has a rejected node at `2024-02-19 13:45` with `status='fwhm_rejected'`, `v=NaN`, `w=0.0`;
- the recent smoothing change makes `weighted_gaussian_smooth()` leave any zero-weight target node as `NaN`;
- that means a rejected Step 1c node now punches a hole directly into the Step 1d curve, which then shows up as a local discontinuity.

Interpretation:

- this is not a missing-raw-data gap;
- it is a consequence of treating all zero-weight Step 1c nodes the same as truly missing-input nodes.

Likely fix direction:

- distinguish between true missing-input target bins and rejected/failed Step 1c nodes;
- keep masking the final output across real raw-data gaps, but allow the Step 1d smoother to synthesize values through isolated rejected semi-hourly nodes.

Follow-up fix applied:

- `weighted_gaussian_smooth()` no longer forces every zero-weight/NaN target node to remain NaN;
- after smoothing, Step 1d now explicitly sets `y_smooth` to NaN only for nodes whose Step 1c status is `missing_input`;
- this restores smoothing through isolated rejected Step 1c nodes while preserving real raw-data gaps.

## 2026-04-25 Step 1c Runtime Investigation

Observed behavior:

- a fresh SuperMAG run without Step 1c checkpoint reuse now completes the semi-hourly Step 1c stage in about `8` minutes instead of the previously remembered `~30` minutes.

Conclusion:

- this did **not** come from the later cleanup/refactor commits (`300aaa5`, `85260f0`, `e3a3a7b`, `59ca85c`, `dc36b4e`);
- the significant runtime reduction came earlier in commit `319ae83`.

The two fundamental Step 1c changes in `319ae83` that reduce runtime are:

- Step 1c now skips target bins whose target day/bin has no finite input at all (`status='missing_input'`) instead of still trying to estimate them from neighboring days;
- Step 1c now applies the article-aligned acceptance test `sigma <= FWHM_stat` directly, instead of the older and much stricter `2.355 * sigma <= FWHM_stat`, which means far fewer window-expansion iterations.

Quantitative note from the current 2024 run:

- each component has `17,568` semi-hourly targets;
- `7,225` of them (`41.1%`) are now skipped immediately as `missing_input`.

Interpretation:

- the cleanup work removed dead code and reorganized files, but it is not the reason Step 1c became much faster;
- the speedup is mainly due to Step 1c doing less work because of the missing-input short-circuit and the looser article-aligned acceptance rule introduced in `319ae83`.
